# Phase 8A.7 — Volume migration and one approval-gated writer trace

Preflight and one owner-operated physical reconnect on 2026-10-23, branch `phase7-hardware-integration`. This note preserves the historical evidence; current values below are **new observations**, not replacements for the first reconnect. No software volume/mute/routing change, ALSA mixer query, or intentional USB SET was performed by OpenWitty. One authorized GET-only settings snapshot was taken before, and one after, the reconnect under the exclusive lease. The approved Plan B observer **armed but stopped during unplug**, before the new device was initialized; it did not capture a hardware-volume write. No second cycle was attempted.

## Historical operating states and numerical check

See [hotplug observations](PHASE8A1_HOTPLUG_REENUMERATION.md), [mixer research](PHASE8A2_USB_MIXER_INITIALIZATION.md), and the [trace design](PHASE8A6_BOOT_WRITER_TRACE_DESIGN.md). Before the **first** owner-operated reconnect, KDE displayed approximately 45%, PipeWire's `channelVolumes` and `softVolumes` were approximately 0.091123, `route.hw-volume=false`, and ALSA exposed no `PCM Playback Volume`. A read-only CONNECT 2 GET found Speaker **0.00 dB**, Headphones **−27.26 dB muted**. After that reconnect, KDE still displayed ~45%, `route.hw-volume=true`, ALSA exposed `PCM Playback Volume` at step 79/120 (−20.50 dB), a GET found Speaker **−20.50 dB** and Headphones unchanged, and PipeWire's `softVolumes` became ~0.9652. OpenWitty issued no SET; the owner did not change volume/mute/profile.

Using the historical linear value `V=0.091123`:

| Quantity | Calculation | Result |
|---|---|---:|
| Effective requested level | `20 log10(V)` | **−20.807440 dB** |
| Cubic display convention | `100 cbrt(V)` | **44.999671%** |
| Observed Speaker step as linear gain | `H=10^(−20.50/20)` | **0.094406088** |
| Predicted software remainder | `S=V/H` | **0.965223772** |
| Remainder in dB | `20 log10(S)` | **−0.307440 dB** |

The predicted `S` matches the recorded ~0.9652 to the stated precision. [PipeWire's SPA parameter definition](https://docs.pipewire.org/devel/group__spa__param.html) explicitly defines `channelVolumes` as **effective linear per-channel volume**, which may be split between hardware and software, and `softVolumes` as the **software-applied** linear portion. [WirePlumber's settings reference](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html) says `device.restore-routes=true` can restore route properties including sink volume and describes a cubic default UI scale. Thus the observed transition is **strong quantitative evidence for splitting the existing 45% request into a −20.50 dB hardware step and −0.31 dB software correction**. It is not process-level proof of who initiated or sent the original USB write. In particular, `softVolumes` is not itself the hardware value, and a UI percentage is not an ALSA step index.

The installed WirePlumber 0.5.18 `state-routes.lua` loads saved route properties, while `apply-routes.lua` constructs a Route parameter with `channelVolumes` and calls `device:set_param("Route", ...)`. Its [state locations](https://pipewire.pages.freedesktop.org/wireplumber/daemon/locations.html) distinguish persisted route state from configuration. This supports a plausible **policy** path. PipeWire 1.6.9's ALSA backend may translate such an effective route request into a hardware mixer write and quantized software remainder; the historical SPA values fit that behavior, but no captured `Route`→ALSA→USB chain yet proves it. KDE requested/displayed the volume; it is not established as the USB writer. Before the original first reconnect, the then-saved ALSA state lacked a `PCM Playback Volume` entry, weakening *that particular saved-state restore* as an explanation. It does not exclude kernel probe writes, another ALSA client, or an unobserved writer.

### Double-attenuation safety scenario, not acoustic measurement

At a later normal boot the hardware Speaker was read as −20.50 dB while `route.hw-volume=false` and PipeWire again reported software-backed ~−20.81 dB. **If** those physical and digital gains are serial/multiplicative for the active playback path, their sum is ~−41.31 dB. Moving the unchanged KDE request into hardware-backed operation could return effective gain toward ~−20.81 dB, a **potential +20.50 dB change without a KDE percentage change**. The actual acoustic path, stream-specific gains, mute state and any firmware behavior were not measured. Do not create playback or change volume to test this. A future bridge must never infer physical Speaker/Headphone level from a software-backed sink percentage, and must fail closed when hardware state or output target is uncertain.

## Trace capability and strict gate

Read-only metadata confirms installed `7.2.10-1-cachyos` has BTF for `vmlinux` and `snd_usb_audio`, libbpf/compiler tooling and root-accessible tracefs. The only listed `usbcore` tracepoints are device-allocation/state events; there is **no verified USB-control submit/complete tracepoint** here. Tagged kernel source shows `snd_usb_ctl_msg()` takes the USB device, setup fields and data pointer, returns the control-transfer result, and calls `snd_usb_ctl_msg_quirk()` after copying returned data. The fentry/fexit observer at this module helper attached and observed one target request. This validates attachment/filtering for that request, **not** SET-value capture or writer-stack attribution, because no SET was captured.

An offline-compiled, opt-in diagnostic (`tools/diagnostics/fu2_writer_trace.bpf.c`, `fu2_writer_trace.c`) hard-codes VID:PID `29c2:0004`, AudioControl interface 0 / Feature Unit 2 (`wIndex=0x0200`), volume/mute selectors, and UAC2 CUR/RANGE class-control request types. It copies at most eight bytes of matching short control data **inside the kernel after filtering**, plus completion result, monotonic timestamps, task name/PID and a SET call stack. It neither opens USB nor issues requests. The loader requires `--execute` and root, caps the observation at **120 seconds or 256 matching events**, stops on a target transfer/capture error or ring-buffer loss, and detaches links on exit. `--dry-run` was executed without loading/attaching a probe. No bus-wide usbmon capture is planned. A post-test GET-only hardware snapshot is authorized only if the lease is free and useful.

Offline build from the repository root (already performed without attaching a probe):

```bash
clang -O2 -g -target bpf -D__TARGET_ARCH_x86 -Wno-missing-declarations -I/usr/lib/modules/$(uname -r)/build -c tools/diagnostics/fu2_writer_trace.bpf.c -o build-release/fu2_writer_trace.bpf.o
bpftool gen skeleton build-release/fu2_writer_trace.bpf.o > build-release/fu2_writer_trace.skel.h
cc -O2 -Wall -Wextra -Werror -Ibuild-release tools/diagnostics/fu2_writer_trace.c -o build-release/fu2_writer_trace -lbpf -lelf -lz
build-release/fu2_writer_trace --dry-run
```

The approved invocation was `sudo -n build-release/fu2_writer_trace --execute`, with the owner acting only after `ARMED` and a separate instruction. Generated build artifacts and diagnostic output remain untracked. The observer loaded only experiment-owned BPF links; it did not change USB interface ownership. **Do not reuse this command for a reconnect without reviewing its teardown-error stop behavior and obtaining new approval.**

For a future separately approved use, exact SET stack/value availability remains unvalidated. A `SET_CUR` stack from the kernel probe, `alsactl`, PipeWire or another task could strengthen attribution, but task name alone is not policy-source proof; WirePlumber route activity and ALSA control-write context must be correlated. A reconnect cannot explain the separate boot-only sticky failure.

**Preflight deviation:** `bpftool feature probe kernel` was inadvertently run once during capability inspection. It may briefly load feature-test BPF programs. It did not attach a writer trace, issue a CONNECT 2 request, or change audio policy; no experiment data were captured. This was outside the stated no-eBPF-load-before-confirmation boundary and was disclosed to the owner immediately. It will not be repeated.

## One approved Plan B attempt: stopped during unplug

The owner confirmed listeners/amplification were protected and the audio environment was safe, then waited for the separate instruction. The filtered observer passed the kernel verifier, attached its two hooks, printed `ARMED`, and the owner performed exactly one manual unplug/replug. The observer's conservative stop-on-any-target-error rule fired at **t=9.430070 s** on a Feature Unit 2 **mute GET_CUR** returning **−71** in a kernel worker (about **0.370 ms** transfer duration). Its result was `events=1`, `dropped=0`, `status=incomplete`, with **zero SET_CUR observations**. The kernel log placed Feature Unit 2 read failures and device removal in that same unplug interval. This is a teardown read failure, not evidence that the device rejected the later re-enumeration or that the trace observed the volume migration. The observer detached immediately; subsequent passive checks found no experiment-owned BPF program, link, or process. There was no re-arm or second cycle.

After the reconnect settled, passive enumeration again showed **one** CONNECT 2 stereo ALSA playback device and **one** PipeWire sink. The output route now reports `route.hw-volume=true` at the unchanged **85% / approximately −4.23 dB** requested sink level; route `channelVolumes` remained 0.614138 and `softVolumes` became 1.000000. The one authorized post-test vendor-interface GET found physical **Speaker −4.00 dB, unmuted**, and **Headphones −32.40 dB, muted**. Before reconnect the Speaker was **−33.34 dB, muted** and Headphones **−32.40 dB, muted**. Thus the Speaker level and mute state changed while Headphones did not. The post-reconnect Speaker −4.00 dB equals the *currently saved* ALSA step 112 and is close to the 85% PipeWire level. Because the trace stopped before re-enumeration, these facts do **not** distinguish ALSA state restoration, PipeWire/WirePlumber volume migration, mixer-probe writes, or another writer. Do not infer an exact hardware/software decomposition from `softVolumes=1.000000` alone; the PipeWire requested level and reported 0.5 dB hardware step differ slightly.

The owner reported **one brief, low-level “speaker turning on” sound about 20 seconds after reconnect**, with no continuing sound or other reported audio problem. This is subjective timing, not a timestamped acoustic measurement or proof of the writer. The changed hardware Speaker mute and level are a safety-relevant result; no follow-up sound/volume experiment was performed. No USB reset, driver detach, OpenWitty SET, audio-policy change, or production polling change was made.

**Trace limitation and next approval gate:** stopping on any FU2 error correctly enforced the predeclared safety rule, but a legitimate unplug can generate a `−71` read failure before reconnect, making this version unsuitable for reliably attributing reconnect writes. A future observer would need an explicitly reviewed disconnect/reconnect state machine or a different arming point and its own approval. It must distinguish probe extrema/restore SETs from any post-registration −4 dB/other SET. A SET near saved ALSA step 112 or current PipeWire 85% would not alone identify policy origin; a call path plus correlated route/ALSA activity is required. **This attempt did not capture the writer.** No further physical cycle is authorized in Phase 8A.7.

Phase 8B remains blocked on actual writer attribution, boot-only probe consequences, reliable hardware state under both ALSA-control states, output/mute mapping, prevention of stale restoration and dual writers, and a fail-closed control policy.
