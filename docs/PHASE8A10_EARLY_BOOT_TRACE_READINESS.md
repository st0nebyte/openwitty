# Phase 8A.10 — early-boot Feature Unit 2 trace readiness

Research and design only, 2026-10-23. **No reboot, device access, ALSA mixer query, BPF load, trace attachment, boot-file edit, or audio-policy change occurred.** The next boot observation requires a separate approval and a completed value-capture feasibility gate. This document builds on [8A.2](PHASE8A2_USB_MIXER_INITIALIZATION.md), [8A.3](PHASE8A3_BOOT_AND_VOLUME_TRACE_PLAN.md), [8A.4](PHASE8A4_CROSS_PLATFORM_USB_INITIALIZATION.md), [8A.5](PHASE8A5_KERNEL_BUILD_PROVENANCE.md), [8A.6](PHASE8A6_BOOT_WRITER_TRACE_DESIGN.md), [8A.7](PHASE8A7_VOLUME_MIGRATION_AND_WRITER_TRACE.md), [8A.8](PHASE8A8_WRITER_TRACE_HARDENING.md), [8A.9](PHASE8A9_RECONNECT_WRITER_ATTRIBUTION.md), and the [audio architecture](PHASE8_LINUX_AUDIO_ARCHITECTURE.md).

## Decision

**An early boot observer is technically plausible on this installation, but a single-boot experiment is not yet execution-ready.** The running driver is a module absent from the inspected initramfs, and the latest boot's mixer probe occurred several seconds after switching to the real root. This creates a possible attachment window. No tested mechanism currently guarantees both (a) attachment *before* its first Feature Unit 2 request and (b) capture of submitted SET bytes and returned GET bytes without broad USB traffic. A login-launched copy of the 8A.9 observer would miss the probe. Do not schedule a reboot until these gates are met offline or on a separate non-target test system.

The absence of the audio module from the initramfs and the post-switch-root warning make an early real-root loader conceivable. But merely ordering a service before a normal login is insufficient. It must start before udev's relevant modalias load **and** attach to a function that already exists. Attaching to `snd_usb_ctl_msg()` cannot precede loading `snd-usb-audio`; if the same load immediately probes the already enumerated USB device, the mixer may finish before a later loader attaches. Pausing/reordering module load would change initialization timing and could mask the suspected bug. A built-in USB-core hook established before module load could avoid that race, but its ability to capture both short payloads with precise device filtering is not yet validated.

## Mechanism comparison and exact capture contract

Official [boot-time tracing](https://docs.kernel.org/trace/boottime-trace.html) can enable filtered events/dynamic probes at the end of `core_initcall`, before this observed userspace module load. [Bootconfig](https://docs.kernel.org/admin-guide/bootconfig.html) would require a **temporary initrd attachment and `bootconfig` kernel option** on this installation, or another explicitly designed early setup; neither is configured or authorized. [Kprobe event syntax](https://docs.kernel.org/trace/kprobetrace.html) supports module-qualified symbols and memory fetches, but no module-absent registration behavior or installed payload-fetch ABI has been validated for this target. Generic [event tracing](https://docs.kernel.org/trace/events.html) describes available-event formats and filtering; the installed USB event field format remains unverified.

| Candidate | Readiness and drawback |
|---|---|
| Bootconfig with a narrow built-in USB-core entry/return probe | Best *candidate* for observing the first class request without changing module-load order. Could begin before module probing. Must first prove setup fields, submitted OUT payload at entry, completed IN payload at return, return status, per-request pairing and a target-only filter on the installed kernel. A tracepoint that logs only URB metadata is **insufficient**. Dynamic kprobes with memory dereferences may incur faults/overhead; kernel private pointer restrictions may hinder stack symbolization. No actual bootconfig definition is approved or validated yet. |
| Temporary early real-root eBPF observer | Could reuse the Phase 8A.9 event decoder if attached to an already-available USB-core function before audio module load; the existing fentry/fexit hooks at `snd_usb_ctl_msg()` alone cannot guarantee this. Requires a privileged early service, module/udev ordering proof, BPF load and hard stop. Holding the driver back to guarantee attachment would alter the very timing under test. |
| Module-qualified kprobe/fprobe on `snd-usb-audio` | Valuable for call-path attribution after the symbol exists. It cannot simply be attached by the 8A.9 userspace loader while the module is absent; pre-registration and activation behavior needs proof. A secondary narrow probe may be paired with a built-in USB-core observer only if it cannot delay the critical reads materially. |
| USB tracepoint or usbmon alone | Can help with status and timing **if** exact event format includes short setup/data bytes. Cannot be assumed to contain GET return values or userspace origin, and broad bus capture may retain unrelated/audio traffic. Reject a metadata-only or unfiltered capture for the root-cause question. |
| General function graph / stacks on every transfer | Can show flow but usually lacks actual short GET/SET values, produces far more events, and is likely to perturb the SET→GET interval. Not the first-pass method. |

The minimum retained record is a monotonic entry/completion pair with target VID:PID `29c2:0004` (or a securely correlated transient address), endpoint 0, `bmRequestType`, request, `wValue`, `wIndex`, requested/actual length, submitted short SET payload, completed short GET payload, completion result, duration and loss count. Decode only AudioControl interface 0, Feature Unit 2, master channel 0: `wIndex=0x0200`, volume selector 2 or mute selector 1 in `wValue`, UAC2 CUR request `0x01` and RANGE `0x02`. Volume is signed little-endian Q8.8 (`−15360=−60 dB`; resolution `128=0.5 dB`); mute uses its own byte. Entity `0x33` is unrelated. To diagnose sticky detection, retain *all* initial GET_RANGE, saved GET_CUR, test SET/GET pairs, any resolution test, final restore/fallback SET and its completion, plus the warning/control-registration result. A completed SET does not independently prove the final analogue output level.

Before any approved live use, validate the precise installed-kernel hook signature, buffer lifetime, payload fetch, completion semantics, target filter and entry/exit correlation **without connecting the observer to this device**. A limited offline fixture or other non-target machine is preferable. If exact values or first-event coverage cannot be demonstrated, the proposed boot trace is not ready. The 8A.9 observer's value capture during reconnect is useful evidence for its existing hook, but says nothing about whether that hook can be active before the boot probe.

## Timing interference, bounds, rollback and physical safety

Start with the narrowest event-only/value capture that answers the question: no continuous stacks, whole-bus packet recording, userspace stream content or general function graph. Even filtered BPF/kprobes add execution time between SET and GET; short payload copying adds less than symbolized stack capture, but **no zero-overhead claim is justified**. Record probe-to-probe and SET-completion-to-GET-submission intervals and lost events. If an instrumented boot no longer warns, treat that as a possible timing perturbation, not a fix. A warning with incomplete payloads also cannot prove stale readback.

The source can write −60 dB during the test and may attempt **0 dB maximum on the sticky path**, without confirming final restoration. An observation-only reboot therefore still carries a potential loudness/unmute risk. For one future approved boot: stop important playback and recording; independently protect listeners, headphones, speakers and external amplifiers (disconnect or turn external amplification off); do not rely on KDE/software mute or prior CONNECT 2 hardware mute; do not set a new starting volume merely to reproduce the problem. A pre-shutdown hardware GET is not a pre-probe measurement if the interface remains powered or receives boot writes. A post-login GET is already after probe and route restoration.

An approved design needs a **separate temporary boot entry and untouched known-good entry/image**, an operator-readable rollback path, and a trace that automatically disables itself. Candidate bounds: fixed small per-CPU buffer; at most 256 matching Feature Unit 2 events; stop after the probe decision plus a short restoration tail, at most 120 seconds from the first target event and 180 seconds from trace start; fail on loss, target error, wrong device or unexpected audio behavior. Bootconfig/ftrace cannot be assumed to implement that complete hard cap and watchdog merely because the plan states it: verify the stop trigger and post-boot cleanup against the exact implementation **before** changing any boot file. If no autonomous stop can be guaranteed without a userspace watchdog, the watchdog itself must be ordered early enough and tested independently. Preserve the prior boot entry, verify the new one before selection, and restore the original entry/image and remove only experiment-owned trace state after the run or any failure. Raw local trace data should be permission-restricted, short-lived and redacted; only a sanitized summary belongs in Git.

**Minimum viable future single-boot plan, approval gated:** (1) establish a value-capable, target-filtered built-in hook and automatic stop in a non-target validation; (2) prepare a reviewed temporary Limine/initramfs/bootconfig or early real-root entry, retaining an untouched fallback; (3) separately obtain explicit approval for the exact privileged files/commands and one normal boot, plus independent audio-safety confirmation; (4) verify the observer started before the first Feature Unit 2 request, capture the short request timeline and kernel warning/control state; (5) stop, verify loss count, remove temporary configuration and inspect only sanitized results. **The current system has a possible timing window, not a proven execution-ready capture path.** Do not substitute another reconnect: it has already shown the working path and cannot answer the boot-only question.

## No-jump requirements for a later OpenWitty control plane

1. Treat `route.hw-volume=false` and `true` as distinct states. When false, KDE's requested volume may be digitally attenuated while independent physical Speaker/Headphone levels remain active; when true, ALSA/PipeWire may split effective gain across hardware and software. Neither the KDE percentage nor cached ALSA step is a verified physical reading.
2. On startup, reconnect, route capability change or target switch, **read actual hardware Speaker/Headphone level and mute separately** through a validated, serialized, single-owner path before showing or commanding a target. If target, level or mute cannot be verified, reject or suspend hardware volume/mute actions. Never restore remembered software values into hardware implicitly.
3. Do not turn a software-backed sink percentage into a hardware SET during a route transition. Hold intended effective volume and physical output state apart until an approved policy can prove that no gain jump or silent unmute results. A future UI must show uncertainty rather than implying KDE and hardware are synchronized.
4. Prevent dual writers before enabling OpenWitty SET: establish who owns ALSA mixer writes, route restoration, kernel probe writes and OpenWitty vendor-interface writes. A single-owner OpenWitty lease coordinates OpenWitty clients only; it does not block the kernel or PipeWire. Any policy change to avoid competition needs separate design and authorization.
5. Keep one stable PipeWire playback sink; do not equate the hardware's selected *control* channel with the active Linux audio route. Speakers and Headphones retain separate volume/mute. KDE target selection must not copy one output's setting to the other or unmute another output. Apply volume and mute independently; fail closed on ambiguous target or a mismatch between requested and read-back physical state.
6. Avoid cumulative software-plus-hardware attenuation being hidden behind a single unchanged KDE percentage. The historical 45% and 85% transitions show why the bridge must observe both gain stages and report a potentially unsafe migration rather than automatically correcting it with a write. No acoustic gain was measured in those investigations.

Before Phase 8B hardware writes: establish the boot probe's actual control sequence and final attempted value; assess whether its sticky decision is false and whether a kernel fix/quirk changes loudness; establish the userspace hardware-writer chain in a run that actually reproduces a migration/unmute, or safely constrain those writers by approved policy; verify independent hardware level/mute mappings and no-jump behavior in both ALSA-control states. A kernel probe fix and a separate OpenWitty control-plane bridge may address different problems. Neither is selected or implemented here.
