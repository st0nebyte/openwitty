# Phase 8A.6 — Early-boot USB writer attribution: trace design only

Research/design, 2026-10-23. **No trace was enabled, no device or ALSA mixer was queried, and no reboot, reconnect, USB request, audio-policy change, or kernel change was made.** Both experiments below require separate approval. This note complements [8A.1](PHASE8A1_HOTPLUG_REENUMERATION.md), [8A.2](PHASE8A2_USB_MIXER_INITIALIZATION.md), [8A.3](PHASE8A3_BOOT_AND_VOLUME_TRACE_PLAN.md), [8A.4](PHASE8A4_CROSS_PLATFORM_USB_INITIALIZATION.md), [8A.5](PHASE8A5_KERNEL_BUILD_PROVENANCE.md), and the [audio architecture](PHASE8_LINUX_AUDIO_ARCHITECTURE.md).

## Executive decision

**Plan B (one bounded physical reconnect) first**, solely after separate approval: it can validate a narrowly filtered trace and attribute a later restoration SET with less configuration and loudness risk. It cannot explain the boot-only sticky verdict by itself. **Plan A (early normal boot)** is subsequently necessary to capture the failing extrema test, but requires an approved temporary early-start mechanism, a rollback plan, and a volume-safety review. Neither plan is authorized for execution by this document. A generic bus-wide usbmon capture is not the default: it can collect unrelated devices and audio-streaming payloads yet cannot identify a userspace writer on its own.

## Current tracing feasibility (read-only inspection)

Running release is `7.2.10-1-cachyos`. Its installed build configuration has `CONFIG_TRACING`, `CONFIG_FTRACE`, `CONFIG_FUNCTION_TRACER`, `CONFIG_FUNCTION_GRAPH_TRACER`, `CONFIG_KPROBES`, `CONFIG_KPROBE_EVENTS`, `CONFIG_FPROBE`, `CONFIG_BPF`, `CONFIG_BPF_EVENTS`, `CONFIG_TRACEPOINTS`, `CONFIG_BOOT_CONFIG`, and `CONFIG_EVENT_TRACING` enabled; `CONFIG_USB_MON=m`. Kernel BTF at `/sys/kernel/btf/vmlinux` is readable and `bpftool` exists. `tracefs` and `debugfs` are mounted, but this unprivileged session cannot list tracefs, so **the exact available USB/ALSA event names, event fields, probe targets, runtime tracing permissions, and payload visibility have not been verified**. `trace-cmd`, `bpftrace`, and `perf` were not found on the current PATH; their absence is not a kernel limitation. Do not install tools merely for this planning phase.

An after-login trace cannot recover the already-completed early probe. [Kernel boot-time tracing](https://docs.kernel.org/trace/boottime-trace.html) supports event filters and dynamic probes through bootconfig, generally starting after `core_initcall`; the actual `snd-usb-audio` load timing must be checked against that start point before promising coverage. [Bootconfig](https://docs.kernel.org/admin-guide/bootconfig.html) can be supplied through an initrd or kernel configuration, but doing so would change the boot path and requires separate approval. [Kprobe events](https://docs.kernel.org/trace/kprobetrace.html) can be added dynamically and may be suitable for a pre-reconnect capture. No currently verified method records relevant short control data *before* the boot probe without temporary privileged boot/initramfs/bootloader preparation. Those paths remain proposals, not installed capabilities.

## Feature Unit 2 record and decoding contract

Keep only monotonic submit/completion timestamps (same clock), temporary bus/controller and device address, VID/PID correlation, transfer/URB correlation ID, endpoint 0, direction, eight setup bytes decoded as `bmRequestType`, `bRequest`, `wValue`, `wIndex`, `wLength`, short submitted/returned data length and bytes, completion status and duration, plus a narrowly captured call-path or task identity where supportable. Transient addresses/pointers are for local correlation only; do not commit them. Record trace loss/overruns and a method identifier. For independent timelines, record clock source and an explicit clock-alignment event before correlating journal, trace and userspace logs.

Match **AudioControl interface 0, Feature Unit ID 2**: `wIndex=0x0200`; `wValue` high byte is selector 2 (volume) or 1 (mute), low byte is channel (master expected 0, but do not discard other channels without review). UAC2 `CUR=0x01`, `RANGE=0x02`; decode `bmRequestType` direction and class/interface recipient instead of calling all `0xA1` traffic UAC mixer traffic. Volume is signed 16-bit little-endian Q8.8: signed raw ÷ 256 dB (`−15360` = −60 dB, `0` = 0 dB; advertised resolution `128` = 0.5 dB). Record returned range structure and exact length before decoding. Mute is a separate selector/encoding. **Entity `0x33` status reads are not Feature Unit 2**, even if they share a class/interface request envelope. Exclude all isochronous/bulk audio payloads and unrelated USB devices at the earliest feasible filter.

For each GET/SET, pair submission with completion using the transfer ID, then classify success, USB error, short data, or lost counterpart. A SET's successful USB completion proves transfer acceptance, not final physical volume; a subsequent GET can still be stale or cached. Capture both submitted SET value and completed GET value. Record the originally saved probe value separately from the advertised extrema and final attempted fallback/restore. If returned data are unavailable, state that the trace cannot decide false-sticky versus actual sticky behavior; do not reconstruct them from source.

## Writer-attribution chain

| Candidate | Minimum convincing chain | What remains ambiguous without it |
|---|---|---|
| Kernel mixer probe | FU2 SET/GET pair plus stack or function-local event at `check_sticky_volume_control()` / `get_min_max_with_quirks()` and ALSA control-registration result, with matching values and transfer IDs. | A USB SET near the warning alone does not show which branch sent it. |
| Udev-triggered ALSA restore | Specific restore process invocation and ALSA control-write entry (task/PID, control identity, value) linked to a matching FU2 SET and completion. | Udev service timestamp or saved ALSA state alone does not prove a write. |
| PipeWire/WirePlumber route restore | Route/device action, PipeWire-side ALSA control-write task/value, and corresponding FU2 SET/completion; distinguish WirePlumber policy initiator from PipeWire's actual write syscall. | A saved 45% route value or coincident `route.hw-volume=true` is insufficient. |
| Other userspace/kernel writer | Same control-write-to-USB chain or probe stack identifying the other path. | usbmon or USB completion PID may be a kernel worker, not the initiating process. |

Use task identity at the ALSA control API boundary and a low-level USB transfer ID/sequence. Timing proximity is a cross-check, never the sole link. If the kernel queues work asynchronously, a common call stack may be absent; mark attribution unresolved unless a durable request/control correlation survives the queue. No broad process or application-content collection is needed.

## Plan A — one early normal-boot observation (separate approval)

1. **Before authorizing any setup:** review actual initramfs/module loading and available event formats/target symbols using read-only metadata. Validate the proposed filter and buffer-loss detection without accessing CONNECT 2. Confirm the user can safely tolerate a possible probe-induced jump to 0 dB, arrange noncritical playback/recording to be stopped, and agree on manual recovery. Do not use BIOS standby-power changes or a forced physical reconnect.
2. Prepare a **temporary, reviewed** bootconfig/early-initramfs trace only if it can be active before `snd-usb-audio` probes this device. Select a small trace instance with monotonic clock, restricted FU2 control events, fixed buffer and event cap. A bootloader command-line or initramfs change is a separate approval item; record the original boot entry/image and a fallback boot entry first. No permanent logger or broad function graph.
3. During **one naturally scheduled normal start**, record USB AudioControl discovery, FU2 GET_RANGE/current value, each min/max SET and following GET with completion/data, resolution test if any, sticky decision, final restore/fallback SET and completion, ALSA registration/rejection, and later ALSA/PipeWire/WirePlumber activity. Confirm the trace start timestamp predates the first FU2 request. A warning with a missing preceding transfer means the capture is incomplete.
4. An early trace needs an **automatic stop** triggered after the FU2 decision plus a short bounded tail for restoration (proposal: at most 120 seconds after first target event, hard 180 seconds from trace start, or 256 matching control events, whichever first), plus bounded ring-buffer capacity and a post-login watchdog. The exact trigger must be validated for the installed event engine; if not available, do not claim unattended bounding and do not run Plan A. Stop on trace-buffer loss, device error, unexpected loudness, or wrong target. A stop-on-event trigger should disable tracing, not modify USB state.
5. Inspect trace/loss counters and existing logs, redact, then remove only the temporary tracing boot configuration and verify the prior boot entry/image. Do not erase unrelated tracing state. A subsequent ordinary boot should verify tracing is off; no repeated reproductions without renewed approval.

**Limit:** bootconfig event setup generally starts after `core_initcall`; if module probing precedes it, a different approved early mechanism is required. Initial boot may be a different firmware/power state than reconnect. A successful probe while instrumented cannot rule out a timing bug: setup filtering, stacks, payload copies and disk writes can delay the critical SET→GET interval. Record those intervals and compare with historical untraced warnings; prefer a low-overhead first pass and add narrow call stacks only if attribution requires them. The device's pre-probe physical value cannot be assumed from pre-shutdown software state.

## Plan B — one bounded manual physical reconnect (separate approval)

1. Before touching the cable, approve exact trace hooks and verify they are armed with a harmless **trace-only** readiness check, no USB transaction. Record the current stable topology and existing saved-state metadata passively; if independently reading hardware level is later approved, use only OpenWitty's already validated vendor-interface GET, with its single-owner lease, and never concurrently with another OpenWitty control client. Do not query potentially side-effectful ALSA mixer controls.
2. User stops important audio/recording and performs exactly one disconnect/reconnect after explicit go-ahead. Capturing begins **before** disconnect/reconnect and ends within **120 seconds total**, or earlier on error, abnormal device behavior, audible issue, trace loss, or event cap. No software reset, mode change, routing change or deliberate starting-volume adjustment. Existing Speaker level may already be −20.50 dB: a repeated SET at that value is still evidence even if no visible change follows.
3. Collect target FU2 control submissions/completions and narrow probe/ALSA write events, kernel card-add and control-registration results, udev/ALSA restore process evidence, PipeWire/WirePlumber route activity, and passive audio-topology recovery. Prefer a control-only kernel-side filter; if a method cannot prevent capture of audio-streaming payloads, reject it rather than retaining a whole-bus dump.
4. Stop/detach only experiment-owned hooks and verify trace state returns to baseline. Compare actual SET values with any approved independent before/after hardware GET; do not infer physical state from a successful USB SET alone. Report whether user-space writer chain is proven, merely correlated, or absent.

Plan B is lower risk for **trace validation and restoration attribution**, but a clean reconnect cannot negate the ten boot failures. If it finds a restore writer, Plan A still determines the boot sticky mechanism. If it does not, the earlier −20.50 dB transition remains unexplained.

## Hardware baselines, safety and interpretation

- A **last pre-shutdown** vendor GET is not the volume at the next probe: CONNECT 2 may retain power, reset internally, or receive writes during startup. A **post-login** GET is necessarily after kernel probe and possible restoration. A **post-reconnect** GET is after that reconnect's probe/restoration unless explicitly time-bracketed. None substitutes for a true pre-probe read, which may be inaccessible without perturbing timing.
- The validated OpenWitty interface-3 GET can give independent Speaker/Headphone readings only when separately authorized and feasible under the lease. Do not run it in this phase or concurrently with another OpenWitty client. It does not make USB-class volume SETs safe or identify their source.
- Prevent sudden loudness: user stops critical playback, turns down external amplification by a personally chosen safe method *before a future approved run*, and has an immediate manual stop path. The kernel's own extrema probe is potentially audible even though the investigator sends no USB write. Do not intentionally set a new starting volume to force an effect.
- Never enable DFU, driver detach, USB reset, alternate-setting changes, ALSA restore, audio-route changes, or OpenWitty writes. No OpenWitty production polling or GUI changes. Keep the single PipeWire sink.
- Trace output must contain only target control setup and short FU2 data, not audio samples, serial strings, USB descriptors beyond the necessary type/identity, unrelated processes or raw bus captures. Store raw local files with restrictive permissions, finite retention agreed before execution, redact IDs/paths before sharing, and commit only independently authored summaries. Stop and discard a capture that exceeds its privacy scope.

## Approval/rollback checklist and Phase 8B gates

Before **either** live experiment, user must separately approve its exact mechanism, commands/files, privilege use, trigger, duration/event/data cap, audio interruption risk, and rollback; Plan A also needs explicit bootloader/initramfs permission, a fallback boot entry, and assurance the capture begins before probe. Probe attachment, usbmon start, eBPF load, reboot and reconnect are all still forbidden now. The future operator must record initial tracing state, use a uniquely named instance/hooks, arm an automatic stop and manual emergency stop, validate loss counters, and restore only changed settings. On any failure to arm/stop cleanly, abort rather than improvising a broader capture.

Before Phase 8B or production hardware SETs: observe the **actual** Linux boot FU2 sequence and final-level consequences; identify or exclude each restoration writer with a linked ALSA→USB chain; determine whether cached ALSA readback matches independent hardware GET when the control exists; define how the single-owner service handles both ALSA-control-present and -absent states; prevent dual writers and stale route restoration; prove correct Speaker/Headphone targeting and mute without duplicate attenuation; and establish fail-closed behavior when target or physical level is unknown. A kernel mixer fix and an OpenWitty control-plane bridge address different concerns and may both be needed. The existing one PipeWire sink remains the preferred playback destination; no virtual sink is justified by present evidence.
