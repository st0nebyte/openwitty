## Interactive safety confirmation and actual sequence

Before disconnect, the owner affirmed that important playback/recording was stopped; speakers, headphones, amplifiers and listeners were independently protected; external amplification was off, physically disconnected or otherwise independently safe; the owner understood that reconnect might raise/unmute Speaker; and the owner was ready for **one** manual unplug/replug. Immediately before the separate unplug instruction, passive checks again showed CONNECT 2 present, no OpenWitty lease/client, zero listed PipeWire playback/recording streams and closed ALSA playback/capture substreams. No hardware level or mute was changed to prepare.

The owner then physically unplugged while **no observer was armed**. Two passive USB enumeration checks separated by two seconds confirmed absence; `snd-usb-audio` remained loaded and no OpenWitty lease/client was present. Only then was the reviewed observer launched with `sudo -n build-release/fu2_writer_trace --execute`. Its own sysfs checks required another two-second stable-absence interval. Both narrow `snd_usb_ctl_msg()` hooks attached while the device was absent, the ring reader initialized, and it printed `ARMED`. This establishes that absent-device attachment was possible **in this run**; it is not a guarantee on another kernel or module-load state. No broad USB capture, module reload, kernel configuration change or automatic retry occurred.

Only after `ARMED` and a separate instruction did the owner replug **once** to the same port. The observer had a **120-second** active-trace cap, **256 matching-event** cap and **30-second first-target-event** deadline, plus fail-stop on target errors/loss. The first target event arrived at relative **t=19.249190 s**, within the deadline. The capture reached its normal bounded stop with **10 events, zero dropped, status `complete`**; no target transfer/capture error or second target address was reported. The exact wall-clock stop interval was not separately instrumented beyond the observer's 120-second timer/deadline. The process exited normally. Subsequent passive `bpftool` link/program checks and process inspection found **no experiment-owned hook or observer process**. No software USB SET, USB reset, driver detach, DFU operation, route/volume/mute change or repeat experiment was performed. Raw trace output and ephemeral identifiers are not committed.

All ten records target **AudioControl interface 0, Feature Unit 2, master channel 0**. Times below are monotonic seconds relative to observer arming, **not** physical-action timestamps. No endpoint-0 error, short response or ring loss was observed. `GET_RANGE` returned **−60 to 0 dB in 0.5 dB steps** each time. No entity-`0x33` or audio-streaming data was captured.

The kernel worker task was the context for these ten consecutive operations. **Directly established:** the host submitted the three volume SETs; each reported a full-length successful USB transfer, and the first two changed values were returned by immediately following GETs. The final −4.00 dB SET has no immediate FU2 GET in the capture, but the independently authorized later OpenWitty GET found Speaker −4.00 dB. The trace does not measure analogue loudness. The first changed readback appeared within the next millisecond, showing effective readback **during this reconnect**, not during the separate boot-only failure condition.

**Strongly supported, not stack-proven:** this sequence matches the identified CachyOS mixer source: three logical `GET_RANGE` reads to obtain max/min/resolution, saved-volume GET, a sticky test at the minimum, resolution test at saved plus 0.5 dB, then saved-value restore. The source's sticky test can return non-sticky after the first changed readback, so absence of a 0 dB test write is consistent with that path. The reconnect kernel log showed a sticky warning for **unit 5**, not unit 2; the output route later reported hardware volume available. The BPF SET stack records could not be symbolized: `kptr_restrict=2` and even privileged `/proc/kallsyms` inspection exposed zero nonzero symbol addresses. No kernel policy or tracing setting was changed to work around this. Thus the precise function call stack is unavailable, and worker identity alone does not establish a userspace origin.

## Volume and mute attribution, separately

**Volume.** No further FU2 volume SET was captured during the bounded observation after the initial millisecond-scale sequence. The physical Speaker was **−4.00 dB before and after**, while KDE remained **85%**. PipeWire's output route changed from `route.hw-volume=false`, `channelVolumes=softVolumes=[0.614138,0.614138]` to `route.hw-volume=true`, `channelVolumes=[0.614138,0.614138]`, `softVolumes=[1.0,1.0]`. This establishes a change in reported hardware-volume availability and software allocation, **not** a captured software-to-hardware volume migration write. The three captured SETs are strongly attributable to kernel mixer probing/restoration by sequence, but the exact call stack is unavailable. ALSA state already held step 112/−4.00 dB and the saved WirePlumber route already held 0.614138/85%, so an identical-value future write would also be ambiguous without its call path. No later USB SET provides direct evidence of `alsactl`, PipeWire or WirePlumber writing hardware volume in this run.

**Mute.** The only captured FU2 mute operation was an initial `GET_CUR=0` (**unmuted**); **zero FU2 mute SETs** were captured. The physical Speaker was unmuted in both independent OpenWitty settings snapshots, and Headphones stayed muted at −32.40 dB. Therefore the Phase 8A.7 Speaker-unmute event **did not recur** and its cause remains unresolved. The saved ALSA `PCM Playback Switch=true` and pre/post PipeWire route mute `false` are consistent with the observed unmuted state but do not prove any hardware mute writer or exact control mapping. This run cannot establish whether a different path or device-internal behavior caused the earlier unmute.

The existing ALSA state file retained its prior modification time during this test. No `alsa-restore.service` or `alsa-state.service` journal entry appeared in the selected reconnect window; a udev-triggered per-card `alsactl` path may not produce such a journal entry. Absence of an additional FU2 SET within the bounded trace argues against a **new hardware-changing FU2 write** from that path during this run, but does not prove no restoration logic ran or no other control path existed. No ALSA mixer control query was performed.

## Outcome and remaining gates

One ALSA stereo playback PCM and one PipeWire CONNECT 2 sink returned. The post-test GET-only settings read at **2026-10-23 14:14:44 +02:00**, after observer cleanup, found Speaker **−4.00 dB unmuted** and Headphones **−32.40 dB muted**, matching pre-test. The owner explicitly reported **“no problems”** when asked about clicks, dropouts, speaker-on sounds and unexpected volume changes during this reconnect. This is a user auditory observation, not an instrumented audio measurement. No ongoing hardware problem was observed in passive checks.

This is a **complete, loss-free reconnect-only FU2 capture**, and it establishes that Linux's normal reconnect mixer probe itself performs temporary hardware-volume writes and immediate readback. It does **not** identify the writer of the historical **−20.50 dB** or Phase 8A.7 **−4.00 dB/unmute** changes, because those transitions were not reproduced during this test. It does not explain the boot-only sticky rejection. Before Phase 8B, the architecture still needs a no-jump policy in both ALSA hardware-volume states, prevention of competing/stale restoration, independent Speaker/Headphone and mute mapping, and evidence for any userspace-to-USB writer chain before enabling production hardware writes. A separately approved **early-boot** investigation or another carefully designed writer-attribution method may be needed; no second reconnect or new trace is authorized in this phase.
