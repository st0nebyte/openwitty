# Phase 8A.8 — Offline hardening of the Feature Unit 2 writer observer

This phase changes only an opt-in diagnostic, synthetic tests and research notes. **No USB request, ALSA mixer query, BPF attachment, trace session, physical reconnect, or audio-policy change was performed.** A later live attempt requires separate approval. The production GUI and 16/48 Hz polling remain unchanged.

## Why Phase 8A.7 stopped

The observer was armed **before unplug**. During removal, a Feature Unit 2 mute `GET_CUR` returned `−71`; the predeclared fail-stop rule ended the trace at 9.430070 s, before the new enumeration. It captured no SET and identified no writer. This was a workflow error, not a reason to ignore `−71` generally. The revised workflow disconnects the device **before arming**; any negative target transfer result after arming still stops capture.

The observed physical state remains safety-relevant: before reconnect, Speaker was **−33.34 dB muted** and Headphones **−32.40 dB muted**, with PipeWire's route muted, `route.hw-volume=false`, and KDE at **85%** (`channelVolumes=softVolumes≈0.614138`). After reconnect, KDE remained 85%, `route.hw-volume=true`, `channelVolumes≈0.614138`, `softVolumes=1.000000`, Speaker **−4.00 dB unmuted**, and Headphones unchanged. The owner reported one brief, quiet speaker-on sound about 20 seconds later. Under the documented cubic UI convention, 85% corresponds to about −4.23 dB; −4.00 dB is a nearby 0.5 dB hardware step. But the pre-existing saved ALSA `PCM Playback Volume` was **already step 112/120, −4.00 dB**. The value match therefore cannot distinguish PipeWire/WirePlumber migration, ALSA restore, another client, kernel writes, or device-internal behavior. The post-reconnect `softVolumes=1.0` also does **not** reproduce the historical 45% experiment's 0.9652 software remainder.

Mute must be investigated independently. Existing file evidence shows saved ALSA `PCM Playback Switch=true`; the pre-reconnect PipeWire route and physical Speaker were muted, whereas the post-reconnect route and Speaker were unmuted. The older 45% saved WirePlumber route was unmuted, but it is not a measurement of this 85% event. The saved switch value is a candidate restoration input, **not** a captured write or proof that the ALSA switch maps to the physical Speaker bit. If a future complete FU2 trace contains no mute SET, alternatives include an unobserved control path, device-internal/default-state change, loss of coverage, or a mapping assumption that is wrong. A volume SET alone cannot explain the unmute.

## Corrected, separately approval-gated workflow

1. While connected, review existing records and perform only separately authorized read-only preparation. Confirm no competing OpenWitty owner. Protect listeners and external amplification; neither software mute nor a previously observed hardware mute guarantees safe reconnect behavior. Stop important playback/recording.
2. With **no observer armed**, instruct the owner to physically unplug exactly once. Verify absence passively through sysfs/USB enumeration. Do not send a USB request or query ALSA mixer controls.
3. Only while absent, check that `snd-usb-audio` remains loaded and attach the narrowly filtered `snd_usb_ctl_msg()` fentry/fexit links. The loader itself refuses to arm if the target is present or passive absence cannot be established. It requires a **two-second stable-absence interval** and checks again immediately before attach; this reduces but cannot eliminate late teardown races. If module/BTF/symbol/attachment is unavailable, **abort**: do not reload a module, use a broader trace, reconnect-and-retry, or reinterpret the failure as permission to proceed.
4. Confirm the loader printed `ARMED`, its 30-second first-target-event wait and 120-second active-trace timer are running, and no loss/error has appeared. Only then separately tell the owner to reconnect manually. The observer must already be armed before new device initialization. Exactly one reconnect; no automatic retry.
5. Stop on any post-arm target transfer error (including `−71`), short/invalid response, correlation failure, ring-buffer loss, second USB address, unexpected audio behavior, or the 120-second/256-event cap. Detach experiment-owned links and verify cleanup. Do not change audio policy, volume, routes, USB configuration, or driver ownership to recover. If the first FU2 event does not arrive within 30 seconds, stop rather than waiting indefinitely.

This workflow avoids the **known unplug error by design**; it does not prove the device cannot fail during reconnect. The hook belongs to `snd-usb-audio`, not to a per-device USB handle, so it is plausible the module symbol remains attachable after the device is removed. The module might instead be absent or its BTF unavailable. This cannot be verified while the device remains connected without violating this phase's no-disconnect/no-attach restriction. The future live preflight must establish it; failure means no capture, not a fallback. There is a small race between passive absence checks and attachment, so the owner must wait for explicit `ARMED` before replugging.

## Capture and classification corrections

The [identified CachyOS 7.2.10 helper](https://github.com/CachyOS/linux/blob/cachyos-7.2.10-1/sound/usb/helper.c) `snd_usb_ctl_msg()` duplicates the caller buffer, invokes `usb_control_msg()`, copies the temporary buffer back and returns the USB result. The [USB core implementation](https://github.com/CachyOS/linux/blob/cachyos-7.2.10-1/drivers/usb/core/message.c) returns the transferred byte count or a negative error, rather than normalizing successful OUT requests to zero. The [mixer call site](https://github.com/CachyOS/linux/blob/cachyos-7.2.10-1/sound/usb/mixer.c) passes a caller-owned volume/mute SET buffer and treats nonnegative helper returns as successful for its own higher-level operation. The diagnostic, however, needs the actual transferred byte count and separately records a short result. The source corresponding to the installed kernel is highly likely, **not byte-proven**, per Phase 8A.5.

The old observer saved only time at fentry and read the buffer at fexit if `result>=size`. A failed/short SET could therefore lose its **attempted** value, and buffer contents after the helper are a poorer submission record. The new observer copies the 1-byte mute or 2-byte Q8.8 volume **attempted SET value at fentry**, before the helper's internal allocation/transfer, and retains it even if the transfer fails. At fexit it records the raw return, completion time and narrow stack. GET data are copied only after successful completion with sufficient length. Classification requires matching entry/exit identity, nonnegative result equal to expected byte count, exact payload size, monotonic times and target setup. A short OUT is **not** reported as a successful SET. Even a full successful SET proves host transfer completion, **not** the resulting analogue hardware level; only a separately authorized independent GET can support that inference.

The filter uses VID:PID `29c2:0004`, class/interface requests, AudioControl interface 0 / Feature Unit ID 2 (`wIndex=0x0200`), volume selector 2 and mute selector 1, CUR plus volume RANGE only. Entity `0x33`, AudioStreaming interface 2 and unrelated devices are excluded. Volume and mute have distinct record kinds; master volume is signed little-endian Q8.8 only after identity/length validation. Other FU2 channels remain labeled by channel, not silently reinterpreted as master. Only up to eight relevant control bytes are copied. No audio streaming payload or serial is collected.

An inflight record is keyed by PID/TID and records setup plus device pointer; duplicate entry, missing/mismatched exit and map/ring loss fail closed rather than producing a possibly mispaired value. A new bus/device address is accepted for the **first** post-arm target event, then a second address stops the run. Reappearance reusing the same address is not distinguishable by this check alone; the operator must not authorize a second physical cycle. The BPF side caps emitted matching records at 256, while the loader has a 120-second alarm and monotonic deadline. The 30-second first-event deadline is an operational convenience, not proof that enumeration failed. Kernel-worker task names or USB call stacks alone do not prove the userspace **policy** origin; a PipeWire/WirePlumber/ALSA attribution still needs correlated route/control-write evidence. Stack capture may be unavailable; this must be reported, not filled in by inference.

## Offline validation and limits

The BPF object and userspace loader compile against installed build headers; no verifier or attach check was run in this phase. The non-attaching `--dry-run` succeeds. The synthetic harness runs **33 assertions with zero failures** covering volume/mute GET and SET, volume RANGE, non-master channel labeling, wrong VID/PID/interface/entity, short/missing/failed transfers, the `−71` fail-stop, Q8.8 decode, monotonic timing, changed device address, repeated appearance, pre-arm gating, 30/120-second deadlines, 256-event cap, loss policy, and injected cleanup callbacks on pre-load, partial-load and full-resource failure paths. It uses no device, root, BPF or audio service. It cannot simulate the kernel verifier, a module disappearing during physical removal, actual fentry buffer lifetime, stack symbols or analogue volume. Prior Phase 8A.7 attachment validated the old hook while the device was connected, not the new hook while absent.

All loader failure paths converge on freeing the reader and destroying the skeleton, which detaches links; OS file-descriptor closure is the crash fallback. Offline tests exercise the same cleanup ordering through injected destructors, **not** real kernel-link cleanup. A future approved test must explicitly verify no experiment-owned links remain after failure or completion. No trace files or generated BPF artifacts belong in Git.

Static review confirms the diagnostic contains no USB-control sender, no ALSA writer, no automatic tracing path, and requires both root and explicit `--execute` to attach. The synthetic suite is registered as `fu2_observer_offline` in CTest. The full Release suite passed **186/186** tests, the USB call-site safety audit passed, and Git diff checks passed. The live writer, cause of the physical unmute, boot-only sticky mixer failure and safety of future hardware-backed KDE writes all remain unresolved. Phase 8B is still blocked.
