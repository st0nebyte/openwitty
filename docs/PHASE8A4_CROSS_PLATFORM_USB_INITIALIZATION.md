## What the Linux mixer probe actually does

The tagged `mixer.c` implements UAC2 Feature Unit volume discovery with `GET_RANGE` (minimum, maximum, resolution) and `GET_CUR`; it handles the first returned range triplet. The UAC2 getter does not have the USB Audio Class 1 getter's ten-attempt retry loop. The setter maps volume `SET_CUR` to `UAC2_CS_CUR`; transfer errors other than `ETIMEDOUT` may be retried, while a timeout returns immediately. These details matter because an unsuccessful or delayed readback is not equivalent to a truly sticky hardware register.

In `get_min_max_with_quirks`, the tagged source reads range and current value, then calls `check_sticky_volume_control`. That check writes the advertised **minimum and maximum** in turn, immediately reads each back, and labels the control sticky only when both readbacks equal the saved pre-test value. There is no settling delay and no intermediate test value. A failed write or read, or either changed readback, avoids the sticky verdict. On the sticky path the code writes maximum as a defensive fallback before returning `-ENODEV`; on a successful check it restores the saved value after resolution handling. Thus even mixer *discovery* can issue host-to-device volume SET_CUR requests. OpenWitty did not issue these writes.

The control-information callback can initiate the range/probe path if it has not run yet. This is why an apparently read-only `amixer`/ALSA control-information query is excluded from the passive boot procedure. A [submitted upstream discussion/patch](https://lists.openwall.net/linux-kernel/2026/08/15/722) addresses false sticky detection for asynchronously updated controls with additional settling/validation. Its proposed delayed/multi-value logic is **not present in the identified CachyOS 7.2.10 tag**; submission does not establish upstream acceptance, applicability to CONNECT 2, or a safe local fix. No CONNECT 2-specific quirk or runtime quirk override was established. `/sys/module/snd_usb_audio/parameters/quirk_flags` showed no explicit runtime overrides; this is not an exhaustive audit of built-in quirks.

The boot log's `2:0: sticky mixer values (-15360/0/128 => ...), disabling` denotes **mixer unit 2, channel 0**. The range values are kernel-reported probe values, not measured Speaker/Headphone output levels. A stale GET_CUR response after a successful SET_CUR is a plausible false-positive mechanism, but the current logs do not include the individual transfers or readback delay, so it remains a hypothesis. A genuine device behavior difference, descriptor/range interpretation, or readiness difference also remains possible.

## Repeated boot warning and distinct AudioStreaming timeout

Accessible historical kernel journals show the unit-2 sticky warning **and** a later `2:0: usb_set_interface failed (-110)` on ten fully visible initial boots from 2026-10-16 through 2026-10-22. The sticky readback varies (`-7936`, `-6912`, `0`, `-6016`, `-6363`, `-5248` across those boots), while the advertised range in the warning remains `-15360/0/128`. In five visible non-boot re-enumerations, the unit-5 sticky warning appears without the unit-2 warning or this timeout. Only the two 2026-10-20 reconnects are confirmed owner-operated physical reconnects; the other non-boot enumeration causes are not established. This is a repeatable **boot-versus-re-enumeration association**, not yet a causality test.

For the current boot, journal monotonic ordering was: USB enumeration about `2.078 s`; unit-2 sticky warning `10.915 s`; unit-5 warning `10.919 s`; `snd-usb-audio` registration `10.928 s`; user-session PipeWire/WirePlumber startup about `11.673 s`; interface timeout `16.991 s`. The timeout follows the mixer warning by about six seconds. The tagged `endpoint.c` formats this warning with **`ep->iface` and `altset`**. Therefore its `2:0` identifies **AudioStreaming interface 2, alternate setting 0**, not Feature Unit 2/channel 0. The code calls `usb_set_interface` while deselecting/configuring an endpoint and retries `-EPROTO`, not `-ETIMEDOUT` (`-110`). Existing logs do not reveal which caller requested this particular alternate-setting operation, whether an audio client provoked it, or any related USB transfer detail. Playback topology later remained available. The two warnings may share a boot-readiness problem, but they arise from distinct kernel paths and one is not proven to cause the other. WirePlumber startup between them is timing evidence, **not** writer attribution.

## The separate hardware-volume writer question

The first observed physical reconnect made the ALSA `PCM Playback Volume` control available and coincided with Speaker changing from 0.00 dB to -20.50 dB; Headphone did not change. PipeWire then reported `route.hw-volume=true` instead of the boot's `false`. The earlier WirePlumber saved route was near KDE's 45% display, and later ALSA state held step 79/-20.50 dB. Both are candidate inputs to restoration, not proof of who performed a write. The first reconnect's then-inspected ALSA state lacked the playback-volume entry; the subsequently saved state acquired one, so a later ALSA restore has a stronger candidate than the first did. A later normal-boot GET found Speaker at -20.50 dB, but cannot distinguish hardware persistence from a boot-time restore.

## Windows handoff: established post-initialization facts and limits

The sanitized Windows investigation reports Windows 11, CONTROL CENTER 5.2.2 and LEWITT driver 5.68.0.26708. `LEWITT_USB_audio_driver.sys` owns the CONNECT 2 USB device, `LEWITT_USB_audio_driverks.sys` provides the Kernel Streaming audio interface, and Microsoft `audioendpoint.inf` registers endpoint abstractions. CONNECT 2 is **not** bound to Microsoft's `usbaudio2.sys`. The separate LEWITT ASIO DLLs are not shown to handle ordinary Windows system-volume requests. This dedicated driver stack is the first **confirmed platform difference** from Linux's standard `snd-usb-audio` path; it is not evidence for a missing proprietary initialization command.

Windows exposes one stereo playback endpoint (Output L/R) and Microphone, Instrument, and Loopback L/R capture endpoints. The driver reports hardware volume/mute capability and a −60 to 0 dB range in 0.5 dB increments. With CONTROL CENTER not running, the reported playback endpoint state was 0 dB, scalar 1.0, unmuted. An endpoint capability or reported level does **not** identify the underlying USB control, prove that Feature Unit 2 is used, establish which physical Speaker/Headphone level it maps to, establish an always-unity audio path, or prove CONTROL CENTER was unnecessary at initial attachment.

Four earlier USBPcap captures covered **normal operation after initialization**. The handoff reports 7,042 paired control transactions, no completed control errors, no Feature Unit 2 requests, no UAC Feature Unit volume `GET_CUR`, `SET_CUR`, or `GET_RANGE`, and no USB **vendor-request-type** transfers in that window. Of these, 7,040 were periodic 64-byte and 128-byte state reads to entity `0x33`, with setup tuples `0xA1/0x03/0x0102/0x3300` and `0xA1/0x03/0x0100/0x3300`, respectively. These are CONNECT 2-specific messages carried in a **class/interface request envelope** (`0xA1`); their `0x03` request code must not be mistaken for a Feature Unit 2 volume GET_CUR, and their absence from the USB vendor-request-type category does not make their payloads generic UAC volume controls. The two other paired transactions are not characterized by the handoff and are not interpreted here. The negative findings apply only to the captured post-initialization windows, not Windows driver enumeration, CONTROL CENTER startup, or system-volume interaction outside those windows.

The Windows endpoint's reported −60…0 dB/0.5 dB capability resembles the Linux unit-2 warning's range `−15360/0/128` in Q8.8 units, but numeric compatibility is **not a mapping proof**. The Windows driver could validate the same UAC Feature Unit differently, expose a different hardware-backed mechanism, or report a capability without using Feature Unit 2 for normal volume operations. Existing evidence does not choose among these possibilities.

The minimum comparisons for competing hypotheses are:

- **H1, Linux false-positive sticky detection:** device accepts effective Windows (or later Linux) range writes while initial Linux immediate readback stays at the pre-test value; a delayed readback changes. Need actual per-transfer timing and values, not just a successful Windows slider.
- **H2, readiness/timing:** identical descriptors but differing response latency or startup ordering between initial enumeration and later reconnect, ideally including the moment the device begins returning coherent GET_CUR. Correlation alone is not proof.
- **H3, required Windows extra initialization:** a reproducible vendor or class request **before** successful volume probing that Linux omits, plus an independently controlled test later; mere presence of proprietary requests is insufficient.
- **H4, different Windows validation:** Windows avoids Linux's min/max immediate-readback test or tolerates delayed readback, yet exposes a functional hardware volume. Need request sequence/driver behavior, not endpoint labels.
- **H5, Linux stale-volume restoration:** a host-originated SET_CUR or vendor volume SET matching the old saved value on Linux and absent (or handled differently) on Windows; writer must be attributed, not inferred from a 45% match.
- **H6, independent issues:** separate transfer/call-stack chains and timing for mixer rejection and later restoration. This remains the default analytical separation until evidence joins them.

Windows evidence should be classified as observed transfer, driver-reported property, inference, or unknown. The dedicated driver makes Linux's generic min/max immediate-readback algorithm **less suitable as an assumed description of Windows**; it does not disprove a Linux false-positive sticky result. Conversely, a working Windows hardware-volume endpoint does not establish that Windows tested, accepted, or even used Feature Unit 2. An enumeration-complete trace may answer USB request order and timing, but not necessarily the driver-internal validation algorithm or originating process.

## Architecture implications and validation gates

The **one existing PipeWire playback sink remains the preferred user-facing destination**; Windows also exposes one stereo playback endpoint, though its driver architecture differs. The Linux boot/reconnect discrepancy changes hardware-volume capability, not functional sink count. A virtual sink is not justified by current evidence. A future OpenWitty control-plane bridge could in principle read the independent vendor-protocol Speaker/Headphone states **regardless of whether ALSA exposes PCM Playback Volume**; its feasibility for KDE intent/display synchronization, unity playback, safe writes and coexistence is still unproven. ALSA control availability must be treated as a separate runtime capability, not a prerequisite for reading OpenWitty state or an automatic authorization to write.

The bridge must explicitly handle both `route.hw-volume=false` and `true`: it must never interpret the boot-time soft sink percentage as current Speaker/Headphone hardware level; must not let saved ALSA/WirePlumber route volume silently overwrite hardware on reconnect; must avoid a second digital attenuation stage; and must prevent the ALSA mixer and an OpenWitty service from competing over the same register. Selected physical control channel must not be treated as proof of playback route or volume target. The vendor-driver distinction alone does not justify replaying any Windows initialization request, changing the Linux driver, or bypassing USB safety gates.

Candidate remedies are **not implementation decisions**: a reviewed kernel timing fix or device-specific quirk if H1/H2 is proven; a targeted restoration-policy change only after the writer is identified; or a single-owner OpenWitty control-plane bridge with explicit PipeWire/WirePlumber intent/display synchronization after both hardware mixer states are characterized. A broad mixer disable, global restore disable, virtual sink, kernel patch, or USB reset would be premature and could regress other devices.

Before any Phase 8B hardware writes: (1) obtain enough approved Windows initialization evidence to avoid assuming Feature Unit 2 or copying unknown commands—W1 is a first reconnect comparison, not a cold-boot substitute; (2) identify the actual Linux volume writer with a separately approved, time-correlated trace or equivalent evidence; (3) establish whether the ALSA control maps only Speaker or also Headphone and whether kernel probe writes are safe; (4) show a no-jump, no-double-attenuation policy for both route states at natural boot and reconnect; (5) test targeting/mute/feedback-loop logic without hardware writes; and (6) seek explicit approval for any subsequent device-write validation. No USB write, trace, driver change, routing change, or service split is authorized by this document.
