## Identified 7.2.10 probe and significant paths

The UAC2 Feature Unit volume control is built by `__build_feature_ctl()`, which calls `get_min_max_with_quirks()`. `get_ctl_value_v2()` maps maximum, minimum and resolution requests to class/interface `GET_RANGE` (`0x02`) and extracts one triplet; its current-value call uses `GET_CUR` (`0x01`). It has no UAC2 GET retry loop. `snd_usb_mixer_set_ctl_value()` maps UAC2 `SET_CUR` to request `0x01`; it can retry transfer errors except timeout. `snd_usb_set_cur_mix_value()` really sends that USB SET when writable and updates a cache on success; `get_cur_mix_raw()` bypasses that cache for probe readback. For Feature Unit 2 master volume, source/descriptor-derived targeting is selector 2, channel 0, interface 0 (`wValue=wIndex=0x0200`), **not a captured Linux setup packet**.

| Path | Source behavior | Possible final hardware state; what is unknown |
|---|---|
| Range GET failure | `get_min_max_with_quirks()` seeds fallback min/max/res, then returns `-EAGAIN` if max or min cannot be read; no extrema SET in that path. | No probe-induced volume change established; a partially built control can be uninitialized. A later `mixer_ctl_feature_info()` call can retry probing, so an ALSA information query is not safely passive. |
| Initial saved `GET_CUR` fails | Branches to `no_checks`, marks initialized and calls `init_cur_mix_raw()`; that helper may SET the minimum if it cannot read current state. | Even failure to obtain a saved value is not a blanket guarantee of no write. The actual outcome depends on later read/cache behavior. |
| Extrema test returns changed readback | `check_sticky_volume_control()` tests min then max, skipping a value equal to saved. For each tested value: SET, immediately raw GET. It declares non-sticky when GET returns **anything different from saved**, not necessarily the test value; no tolerance or explicit settlement delay. Then `check_volume_control_res()` may do additional step-value SET/GETs. Finally the function attempts a SET back to saved. | Temporary min/max or step-value changes are possible. The final restoration SET result is **ignored**. No final readback verifies the true physical level. |
| Test SET or GET fails | Sticky checker treats a transfer failure as non-sticky. It may then run the resolution check and attempt saved-value restoration; timeout is not retried by the setter. | A completed earlier SET could have changed hardware even when a later GET fails. Restoration can fail unnoticed. |
| Both applicable test GETs equal saved | Without a relevant `MIXER_GET_CUR_BROKEN` quirk, checker logs `sticky mixer values ... disabling` and returns `-ENODEV`; control registration is skipped. `get_min_max_with_quirks()` does **not** restore saved here. It instead attempts to SET the advertised maximum on master/all applicable channels before returning. | For this reported range max is **0 dB**. If the control is actually functional but readback lags, this can leave it at 0 dB, or at another test/intermediate level if writes fail/delay. The maximum fallback's result is not verified. The observed warning proves the classification, not the resulting physical volume. |
| Existing `MIXER_GET_CUR_BROKEN` quirk path | Old checker marks GET_CUR broken and returns `-ENXIO`; `no_checks` clears cache and `init_cur_mix_raw()` can SET the minimum when cached read is unavailable. | This old optional quirk is not a demonstrated safe CONNECT 2 remedy; it can replace a hardware level with minimum. No applicable CONNECT 2 quirk was established. |

The probe may run at initial USB mixer construction; uninitialized controls can also enter it from `mixer_ctl_feature_info()`. Boot and reconnect are distinct enumeration/readiness contexts. Once a volume control is rejected as sticky and freed, ordinary later control-info access does not automatically resurrect that discarded control in the same enumeration. A successful cache update records a requested value, not necessarily physically settled hardware. These are reasons to avoid mixer queries during passive boot observation.

It is not a generic fix for the boot failure. |

**Critical newer-path risk:** inspecting the source after both commits shows that when the checker sets `get_cur_broken=1` and returns `-ENXIO`, `get_min_max_with_quirks()` goes to `no_checks`, clears the cache, and later calls `init_cur_mix_raw()`. `snd_usb_get_cur_mix_value()` then returns `-ENXIO` because reads are marked broken; `init_cur_mix_raw()` attempts a SET to **`cval->min`**. For the reported master range that is −60 dB. Thus retaining the ALSA control can replace the old maximum fallback with a **minimum write**. The follow-up can clear the broken-read flag afterward for a device with `MIXER_GET_CUR_OK`, but does not retroactively remove that initialization write. This is a source-level path, not an observed CONNECT 2 result. Both upstream changes affect other UAC devices globally, so applying them without device-specific validation could cause jumps, wrong reported levels or ineffective sliders. No kernel patch, quirk or rebuild was installed or tried.

A separately [proposed more precise sticky test](https://lists.openwall.net/linux-kernel/2026/08/15/722) changes test count and adds 10 ms pauses, but was **not** either of the two commits above and is absent from the identified 7.2.10 path. It may reduce a false positive but increases extrema/intermediate hardware writes and cannot be deemed safe without changed-value readback and audible-impact evidence.

## Windows W1 and the separate restoration question

The owner-reported Windows W1 **physical reconnect** used the dedicated LEWITT driver with CONTROL CENTER closed: Feature Unit 2 `GET_RANGE` succeeded, volume `GET_CUR` returned 0 dB, one `SET_CUR` wrote that *same* 0 dB, and another GET returned 0 dB. There was no Linux-style min/max test. Its 0.184 ms SET-completion-to-next-GET-submission gap does not measure settling after a **changed** value. Windows W1 is not a cold-boot reproduction; Linux already exposes the ALSA volume after physical reconnect. It strengthens the case for scrutinizing Linux's algorithm but does not establish a false sticky verdict, timing threshold, or missing proprietary initialization command.

The earlier Linux Speaker transition to −20.50 dB remains separate. Kernel extrema/restore writes, udev `alsactl restore`, WirePlumber/PipeWire route restoration, another writer, and hardware persistence remain candidates. Neither W1's unchanged 0 dB SET nor matching saved Linux values attributes that write. The [writer-attribution trace plan](PHASE8A3_BOOT_AND_VOLUME_TRACE_PLAN.md#future-separately-approved-writer-attribution-trace) remains approval-gated.

## Ranked decisions and evidence gates

1. **Now, noninvasive:** retain the one PipeWire sink and read-only OpenWitty GUI. Do not infer that a present ALSA hardware control is both trustworthy and safe to restore. Archive/compare the historical package recipe and source tarball against `.BUILDINFO` if they become available; match module debug information/build ID if possible. Current package-to-file identity is exact, but source-to-binary identity is not.
2. **Next investigation requiring separate approval:** a bounded, loss-free Linux capture of Feature Unit 2 transfers and writer context during a *naturally occurring* boot or separately approved reconnect, with independent before/after hardware level evidence. It must distinguish kernel probe from ALSA/WirePlumber writes and measure changed-value SET/GET timing without adding test writes. No such trace is authorized here.
3. **Conditional kernel path:** only if the probe is shown to reject an effective control, evaluate a reviewed upstream fix or narrow quirk. Require tests for min/max transients, final hardware level, control readback/caching, Speaker/Headphone mapping, boot/reconnect and other-device regression. The two examined commits do **not** pass this safety gate by inspection alone.
4. **Independent control-plane path:** a future single-owner OpenWitty bridge could read hardware Speaker/Headphone state regardless of ALSA control availability, while preserving one playback sink. It must still prevent concurrent ALSA/WirePlumber hardware writes, stale restore, duplicate software attenuation and output-target jumps. This is an architectural candidate, not Phase 8B implementation authorization.

No kernel fix, device quirk or bridge is selected. The exact Linux volume writer and final physical state after the kernel probe remain unmeasured.
